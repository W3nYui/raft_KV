# KVRaftCpp：项目整体学习导览

> 目标：快速建立“一个客户端请求如何通过 RPC、Raft 和状态机变成一致 KV 数据”的整体心智模型，再进入实现细节。

## 1. 项目是什么

这是一个使用 **C++20 + CMake** 实现的 Raft 分布式键值存储学习项目。它把几个通常独立学习的主题放在同一条链路中：

- 用户态协程、调度器、`epoll` 和 Hook 组成的并发运行时；
- 基于 Protobuf 和 TCP 的自定义 RPC 框架；
- Raft 的选举、日志复制、提交、持久化和快照；
- 以 `KvServer` 为状态机的读写服务、`Clerk` 客户端重试，以及跳表数据结构。

项目没有根目录 `README.md`，因此应先把 `docs/目录导览.md` 和顶层 `CMakeLists.txt` 当成入口，而不是直接打开 `src/raftCore/raft.cpp`。

## 2. 一张全景图

```mermaid
flowchart LR
    Client[Clerk 客户端] -->|Get / Put / Append RPC| KVRPC[kvServerRPC.proto]
    KVRPC --> KV[KvServer 状态机]
    KV -->|Start(Op)| Raft[Raft 核心]
    Raft -->|RequestVote / AppendEntries / InstallSnapshot| RaftRPC[raftRPC.proto]
    RaftRPC --> RPC[自定义 RPC + Protobuf + TCP]
    RPC --> Peers[其他 Raft 节点]
    Raft -->|ApplyMsg| KV
    KV --> Store[KV 数据与快照]
    Fiber[协程运行时 + epoll] --> RPC
    Fiber --> Raft
```

系统的关键分界是：`KvServer` 负责业务状态机，`Raft` 只负责让各副本以相同顺序提交命令；RPC 负责跨进程传输；Fiber/IOManager 负责不阻塞工作线程的并发执行。

## 4. 两条最重要的数据流

### 写入：`Put` / `Append`

1. 调用方进入 `src/raftClerk/clerk.cpp` 的 `Clerk`，带上稳定的 `clientId` 与递增的 `requestId`。
2. `Clerk` 通过最近领导者优先、失败后轮换节点的策略，调用 `kvServerRpc.PutAppend`。
3. `src/raftCore/kvServer.cpp` 把业务请求封装为 `Op`，交给 `Raft::Start`；它不会在本地立刻修改已提交状态。
4. `src/raftCore/raft.cpp` 将命令追加到领导者日志，使用 `AppendEntries` 复制给多数派。
5. 多数派确认后，领导者推进 `commitIndex`，并通过 `ApplyMsg` 将已提交命令交给 `KvServer`。
6. `KvServer` 执行 Put 或 Append，记录请求去重信息，并唤醒等待该日志索引结果的请求。
7. 结果沿同一 RPC 链路返回客户端；若领导者变化或网络失败，客户端保留原请求标识后重试。

### 读取：`Get`

1. `Clerk::Get` 采用与写入相同的领导者重试策略。
2. `KvServer::Get` 检查当前节点的领导者状态与请求去重/等待逻辑，再从 KV 状态机取值。
3. `GetReply` 通过 `kvServerRPC.proto` 定义的字段回传值、错误状态和领导者相关结果。

阅读时要明确区分：网络调用成功不等于命令已提交；日志已提交不等于上层状态机已应用；请求重试不等于可以重复执行写操作。

## 5. 从网络到函数调用：RPC 链路

`src/rpc/rpcheader.proto` 定义请求帧的服务名、方法名和参数长度。`MprpcChannel::CallMethod` 序列化请求头和参数，通过 TCP 发送；`RpcProvider` 在服务端解析帧、定位 Protobuf 服务方法、执行后写回响应。

这套设计中最值得掌握的点是 TCP 是字节流，没有天然消息边界。因此参数长度是正确切帧的必要条件；不要把它当成仅用于调试的元数据。`RpcController` 承载单次调用错误，`RpcChannel` 负责传输和编解码，二者不要混为一谈。

协议文件是唯一可信的接口源：

- `src/raftRpcPro/kvServerRPC.proto`：客户端的 `Get`、`PutAppend` 以及请求去重所需标识；
- `src/raftRpcPro/raftRPC.proto`：`RequestVote`、`AppendEntries`、`InstallSnapshot` 等 Raft 控制消息；
- `src/rpc/rpcheader.proto`：底层自定义 RPC 帧头。

## 6. 并发运行时：为什么先学 Fiber

Raft 需要定时选举、周期心跳、并发 RPC 和 I/O 等待。项目通过 `src/fiber` 的用户态 Fiber 来承载这些工作：

- `fiber.cpp`：上下文、恢复、让出与状态管理；
- `scheduler.cpp`：在线程池中调度 Fiber 或回调；
- `iomanager.cpp`：用 `epoll` 接收事件，并把就绪事件投回调度器；
- `timer.cpp`：支持选举超时和心跳等定时任务；
- `hook.cpp`：将部分阻塞式系统调用转换为“当前 Fiber 让出”。

这里是用户态 Fiber 实现，而非 C++20 `co_await` 关键字协程。阅读时应追踪 `resume`、`yield`、`run`、`idle` 之间的状态转移，并用 `example/fiberExample` 验证直觉后，再研究 Raft 的定时器与 RPC。

## 7. Raft 核心：建议按状态机而非文件顺序读

`src/raftCore/raft.cpp` 是最复杂的实现文件。推荐围绕下列主题跳转阅读：

| 主题 | 关键函数/对象 | 需要验证的不变量 |
| --- | --- | --- |
| 选举 | `electionTimeOutTicker`、`doElection`、`RequestVote` | term 单调递增；每个 term 至多投一票；日志更新者才能获选 |
| 心跳与复制 | `leaderHearBeatTicker`、`AppendEntries1`、`sendAppendEntries` | `prevLogIndex/prevLogTerm` 匹配后才能追加；冲突后回退 `nextIndex` |
| 提交 | `leaderUpdateCommitIndex`、`applierTicker` | 仅多数派确认的当前 term 日志可推进提交；按顺序应用 |
| 快照 | `Snapshot`、`InstallSnapshot`、`CondInstallSnapshot` | 截断后日志索引仍可正确换算；落后节点能追上 |
| 恢复 | `persist`、`persistData`、`readPersist` | 重启后恢复 term、投票、日志和快照边界 |

`raft.h` 应先于 `raft.cpp` 阅读：它集中给出角色、日志、`nextIndex`、`matchIndex`、提交位置、持久化器和应用通道等状态，帮助你避免在大文件中失去上下文。

## 8. 从共识到业务状态机：`KvServer`

`src/raftCore/kvServer.cpp` 是“Raft 算法”和“用户可见 KV 接口”之间的适配层。它负责：

- 接收 `Get`、`PutAppend` RPC；
- 将写操作转成 `Op` 并送入 `Raft::Start`；
- 消费 `ApplyMsg`，只对已经提交的命令修改 KV 状态；
- 基于 `clientId/requestId` 避免客户端重试造成重复写入；
- 通过等待通道把日志索引与原始客户端请求关联；
- 在 Raft 状态过大时创建、安装和恢复快照。

这是复制状态机模式真正落地的位置。调试写入问题时，应沿“客户端请求 → 日志索引 → 提交位置 → ApplyMsg → 状态机执行 → 响应唤醒”逐段检查，而不是只看网络返回值。

## 9. 存储、客户端和示例

`Persister` 保存 Raft 状态和快照；`ApplyMsg` 是共识层交给状态机的消息边界。`Clerk` 只把领导者缓存作为性能优化，任何请求都必须允许领导者已经变化。

`src/skipList/include/skipList.h` 是一个独立的模板跳表学习材料，包含随机层高、插入、查询、删除、覆盖写与 Boost 文本归档。它解决的是单副本数据组织，不解决副本一致性；不要把跳表与 Raft 的职责混淆。当前查询路径未加锁，调用方需要评估读写并发边界；其独立构建入口也较轻量，因此不要假设它已完整替代主 KV 状态机的所有存储路径。

端到端串联请从 `example/raftCoreExample/raftKvDB.cpp` 和 `caller.cpp` 开始：前者启动多个 `KvServer`，后者发起客户端调用。它们是验证端口、节点配置、领导者选举和请求重试的最佳起点。

## 10. 注意事项与常见误区

1. **不要编辑 `*.pb.h` / `*.pb.cc`。** 它们是 `.proto` 的生成物；接口变更应修改 `.proto` 后重新生成。
2. **先使用 CMake 工程构建。** 顶层配置要求 C++20，并设置了全局 include/link 路径；脱离工程单独编译易发生依赖或标准版本不一致。
3. **外部依赖需先具备。** 工程链接 Muduo、Protobuf、pthread、`dl`，跳表还使用 Boost 序列化相关能力。
4. **全局 include 路径要小心。** 顶层 `CMakeLists.txt` 通过多条 `include_directories` 暴露头文件，便于学习但会弱化模块边界；新增模块时优先明确自身依赖。
5. **Raft 修改必须以不变量为准。** 不能只通过单节点“能跑”判断正确性；至少覆盖多节点、网络失败、领导者变更、重复写、重启恢复和快照安装。
6. **测试覆盖仍偏基础。** `test` 主要验证工具能力；当前 GitHub Actions 关注问候和贡献者名单，不是完整的构建/测试门禁。
7. **分清时间与并发边界。** Fiber Hook、定时器、锁和网络回调共同影响执行顺序；排查卡住问题时先判断是 Fiber 未被恢复、`epoll` 事件未到、锁未释放，还是 Raft 等待多数派。
8. **快照不是普通持久化。** 它会改变日志的有效起点；所有日志索引转换和落后副本补齐逻辑都必须同时考虑快照边界。
