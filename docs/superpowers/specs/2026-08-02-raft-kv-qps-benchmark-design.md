# Raft KV QPS 压测工具设计

日期：2026-08-02
状态：已确认，待实现

## 1. 背景

项目已经提供了基于自定义 RPC 的 Raft KV 集群、`Clerk` 客户端和 `callerMain` 示例，但目前没有用于稳定测量吞吐量的压测工具。现有 `callerMain` 固定串行执行请求，且 `Clerk` 在 RPC 失败或请求落到非 Leader 时会无限重试，无法可靠统计失败数和单次操作耗时。

本任务新增一个独立的 C++ 压测可执行文件。压测工具假定 Raft 集群已经正常启动，不负责启动或清理集群进程。

## 2. 目标与非目标

### 目标

- 通过现有 `Clerk` 和 RPC 路径测量真实 KV 操作吞吐量。
- 支持固定的全局操作总数和可配置并发客户端数。
- 支持 `Get`、`Put`、`Append` 混合负载，默认权重为 `1:1:1`。
- 为每个操作设置超时；超时、连接失败和有限时间内无法找到 Leader 的请求计为失败，并继续后续操作。
- 使用变化的 Key 和 Value，避免所有请求使用同一输入。
- 结束时输出中文统计报告，包括成功数、未命中数、失败数、耗时和 QPS。
- 保留现有普通 `Clerk` 接口的行为，避免破坏当前示例。

### 非目标

- 不负责启动、停止或探测 Raft 集群进程。
- 不修改 `.proto` 文件或任何生成的 Protobuf 文件。
- 不引入新的测试框架或重构 Raft 共识逻辑。
- 不在压测过程中逐条打印请求。
- 不实现延迟百分位、分布式压测控制器或跨机器压测。

## 3. 使用方式

新增可执行文件 `qpsBenchmark`，运行时需要传入已经由集群生成的配置文件和操作总数。例如：

```bash
./bin/qpsBenchmark \
  -f bin/checkChange.conf \
  -n 1000 \
  -c 4 \
  -k 100 \
  -t 1000 \
  -s 42
```

参数定义如下：

| 参数 | 含义 | 默认值 |
| --- | --- | --- |
| `-f` | Raft 节点配置文件 | 必填 |
| `-n` | 所有并发客户端合计执行的操作数 | 必填 |
| `-c` | 并发客户端数量 | `1` |
| `-k` | 随机 Key 的数量 | `100` |
| `-g` | `Get` 权重 | `1` |
| `-p` | `Put` 权重 | `1` |
| `-a` | `Append` 权重 | `1` |
| `-t` | 单次操作超时时间，单位为毫秒 | `1000` |
| `-s` | 随机种子 | 当前时间 |

`-g`、`-p`、`-a` 表示权重而不是百分比。例如 `-g 2 -p 1 -a 1` 表示四次操作中平均两次为 `Get`，一次为 `Put`，一次为 `Append`。

## 4. 整体架构

### 4.1 压测入口

在 `example/raftCoreExample/qpsBenchmark.cpp` 中实现压测程序：

1. 解析命令行参数并校验操作数、并发数、Key 数量、权重和超时必须为合法正数。
2. 创建全局工作计数器，所有线程通过原子递增领取操作序号，因此 `-n 1000` 始终只执行 1000 个逻辑操作。
3. 启动 `-c` 个工作线程，每个线程创建并初始化一个独立的 `Clerk`。
4. 每个线程生成操作和输入，调用压测专用 Clerk 接口，并把结果累加到线程安全统计器。
5. 最后一个线程完成后，主线程根据墙钟耗时和各操作耗时生成中文报告。

每个线程使用独立的 Clerk、连接集合、`clientId` 和请求序列号，避免多个线程共享现有 Clerk 内部状态。总操作领取和统计字段使用原子变量或互斥保护。

### 4.2 客户端扩展

在 `src/raftClerk/include/clerk.h` 和 `src/raftClerk/clerk.cpp` 中增加压测专用结果类型和接口。结果至少区分：

- `Success`：`Put`/`Append` 返回 `OK`，或 `Get` 返回 `OK`。
- `NotFound`：`Get` 正常返回 `ErrNoKey`。
- `Failed`：超时、连接失败、无效响应或截止时间内无法完成请求。

现有无返回状态的 `Put`、`Get`、`Append` 接口继续保留，普通示例仍使用原有的无限重试行为；压测程序只使用新增的带超时接口。

### 4.3 RPC 超时

在 `src/rpc/mprpcchannel.*` 中为 RPC channel 增加可选的收发超时。默认超时值为关闭，以保持现有行为；压测客户端传入 `-t` 指定的超时时间。

在连接建立后设置 socket 的发送和接收超时。Clerk 为每个逻辑操作计算剩余截止时间，并把不超过剩余时间的超时传给当前 RPC 尝试；单次 RPC 超时后关闭当前连接并返回失败，让 Clerk 在剩余时间内切换节点重试。这样一次逻辑操作的总耗时不会因为多次重试而突破操作级超时。RPC 协议格式保持不变。

在 `src/raftClerk/include/raftServerRpcUtil.h` 和 `src/raftClerk/raftServerRpcUtil.cpp` 中透传可选超时参数。Clerk 在每个逻辑请求中保持同一个 `clientId + requestId`，Leader 切换或网络重试不会生成新的逻辑请求，保证写操作的幂等语义。

## 5. 负载生成

### 5.1 操作选择

使用权重随机选择操作类型，默认 `Get:Put:Append = 1:1:1`。权重支持命令行调整，但三者不能同时为零。

### 5.2 Key 和 Value

Key 从 `key_0000` 到 `key_<key-space-1>` 的有限集合中随机选择。有限 Key space 可以让不同操作访问部分相同的数据，避免 `Get` 永远访问完全不相关的新 Key。

Value 使用线程编号、线程内序号和随机片段组合生成，例如：

```text
value_t2_0189_a7f3
```

每个线程使用由全局种子和线程编号派生的独立 `std::mt19937_64` 随机引擎。指定 `-s` 后，每个线程自身生成的操作和输入序列可以复现；并发线程之间的实际交错顺序不作复现保证。未指定时使用当前时间作为种子。

## 6. 并发、超时与统计

### 6.1 并发模型

并发数表示工作线程数，不改变总操作数的含义。操作序号由所有线程共享领取，线程提前完成后不会额外执行操作。

### 6.2 重试模型

每个逻辑操作拥有一个截止时间。收到 `ErrWrongLeader` 或 RPC 传输失败时，Clerk 在截止时间内按节点顺序尝试其他节点；超过截止时间后返回 `Failed`。重试不会无限阻塞，也不会改变该逻辑操作的 request ID。

### 6.3 时间测量

- 总耗时：主线程启动所有工作线程到所有线程结束之间的墙钟时间。
- 平均请求耗时：所有逻辑操作实际耗时之和除以总操作数。
- 总 QPS：总操作数除以总墙钟耗时。
- 成功 QPS：成功操作数除以总墙钟耗时。

单条请求不输出日志，避免终端 I/O 成为压测瓶颈。

## 7. 中文结果报告

报告使用中文标签，至少包含：

```text
========== Raft KV 压测结果 ==========
配置文件：bin/checkChange.conf
并发客户端：4
操作总数：1000
成功操作数：812
Get 未命中数：146
失败操作数：42

总耗时：24209 ms
平均请求耗时：91.37 ms/次
总吞吐：41.31 QPS
成功吞吐：33.54 QPS

操作分布：
  Get：334
  Put：329
  Append：337
=======================================
```

`Get` 的 `ErrNoKey` 单独计入“Get 未命中数”，表示 RPC 已正常完成，不计入成功操作数，也不计入失败操作数。

## 9. 验证方案

1. 使用 CMake 构建 `qpsBenchmark` 目标，确认现有目标仍可构建。
2. 在已经正常启动的 Raft 集群上执行固定操作数压测。
3. 使用 `-c 1` 和更高并发数运行，确认总操作数始终等于 `-n`。
4. 检查成功、未命中和失败三类统计的总和与操作数一致。
5. 使用固定 `-s` 重复运行，确认输入序列可复现；使用不同 Key space，确认请求内容有变化。
6. 设置较小 `-t` 制造超时，确认请求最终计为失败且压测会继续，不会无限阻塞。
7. 确认 `callerMain` 和其他现有示例仍能正常构建。

当前项目的 `Debug` 配置默认开启，服务端调试日志可能显著影响正式 QPS 数值。压测工具本身不改变全局 Debug 配置；正式对比时应记录该配置状态，并在需要真实吞吐数据时关闭服务端逐请求调试输出。

## 10. 风险与取舍

- 自定义 RPC 当前使用同步调用，因此每个压测线程一次只处理一个请求；并发吞吐通过增加客户端线程实现。
- 操作级截止时间依赖底层 socket 超时，超时后的连接需要关闭并重新建立，连接重建成本会体现在结果中。
- Raft 写操作必须等待多数派提交，写 QPS 会受选举、心跳、快照和磁盘持久化影响；报告不把读写结果合并成唯一指标，而是同时输出操作分布和成功数。
- 压测工具只面向单机多节点集群，不宣称代表生产环境或跨机器部署性能。
